# 구종 가치(Pitch Run Value) 설계

- 날짜: 2026-10-04
- 맡은 세션: API 세션(dk-analytics-d1). 요청은 선수 분석 세션(dk-analytics-6e)에서 왔습니다.
- 상태: **evan 검토 대기.** 검토 전에는 표를 만들거나 수집 일정을 바꾸지 않습니다.

## 1. 무엇을 만드는가

공 하나의 가치를 기대 득점의 변화로 잽니다.

    공 하나의 가치 = (던진 뒤 기대 득점 − 던지기 전 기대 득점) + 그 공에서 난 득점

투수 쪽 부호로 바꿉니다. 실점을 막으면 +, 내주면 − 입니다. 이 값을 투수 × 구종 × 타자 손(L/R)별로
더해 미리 계산 표에 넣습니다. 화면은 API 로 그 표를 읽기만 합니다. Worker 는 무료 CPU 한도(10ms)가
있어 요청 때 계산하지 않습니다.

선수 분석 화면은 구종 구사율 가운데 칸에 "좌타 가치 | 구종 | 우타 가치"를 넣습니다.

## 2. 기대 득점 표

- 상태는 주자(1·2·3루 있음/없음 8가지) × 아웃(0~2) × 볼카운트(0-0 ~ 3-2, 12가지) = **288칸**입니다.
- 한 칸의 값은 "그 상태에서 던진 공들이 맞은 반이닝에서, 그 공부터 반이닝 끝까지 난 득점"의 평균입니다.
- 시즌마다 그 시즌 정규시즌 PBP 로 따로 만듭니다(점수 환경이 해마다 다릅니다).
- 정규시즌 거르기는 arsenal 과 같습니다. 경기 ID 가 3333·4444·5555·7777·9999 로 시작하면 뺍니다
  (data_collection/game_type.py, src/lib/gametype.js 와 같은 규칙).

2024 시험 계산(정규시즌 234,741행):

| 상태 | 기대 득점 | 공 수 |
|---|---|---|
| 주자 없음, 무사, 0-0 | 0.616 | 12,562 |
| 주자 없음, 1사, 0-0 | 0.322 | 8,503 |
| 주자 없음, 2사, 0-0 | 0.127 | 6,615 |
| 1루, 무사, 0-0 | 1.062 | 3,694 |
| 만루, 무사, 0-0 | 2.585 | 260 |
| 주자 없음, 무사, 3-0 | 0.976 | 584 |
| 주자 없음, 무사, 0-2 | 0.518 | 3,286 |

288칸이 모두 찼고, 가장 적은 칸도 공이 6개 있습니다.

## 3. 이음새 처리(evan 확인 필요)

데이터에서 확인한 사실(2024):

- 한 경기 안의 순서는 `pbp_id` 순입니다. 타석 번호와 어긋나는 곳이 0곳입니다. `pitchID` 는 140곳이
  어긋나서 쓰지 않습니다.
- 투구가 아닌 행이 11,178개 있습니다(도루, 도루실패, 견제사, 폭투, 포일, 보크, 투수 교체, 대타·대주자).
  이 행에도 그 직전의 주자·아웃·볼카운트·점수가 들어 있습니다.
- `runs_scored` 는 같은 반이닝 안에서 다음 행과의 점수 차이와 221,922건 모두 같습니다. 그래서 득점은
  `runs_scored` 로 셉니다.
- `outs_on_play` 는 믿지 않습니다. 삼진인데 0으로 적힌 행이 있습니다. 아웃은 다음 행의 `outs` 로 봅니다.

처리 방법:

| 이음새 | 처리 |
|---|---|
| 던진 뒤 상태 | **바로 다음 행의 상태**입니다. 다음 행이 도루·견제 같은 사건 행이어도, 그 행에 적힌 직전 상태가 곧 이 공 직후의 상태입니다. |
| 투구 사이 사건(도루, 도루실패, 견제사, 폭투, 포일, 보크) | **공의 가치에 넣지 않습니다.** 사건 행이 따로 있어서, 위 규칙만으로 저절로 빠집니다. |
| 이닝 끝 | 반이닝의 마지막 공 다음은 기대 득점 0 입니다. 그 공의 득점은 넣습니다. |
| 투수 교체 | 따로 처리하지 않습니다. 교체 행은 상태를 바꾸지 않는 사건 행입니다. 공의 가치는 그 공을 던진 투수에게 갑니다. 물려받은 주자가 들어와도 그 공을 던진 투수의 몫입니다. |
| 경기 끝(끝내기, 강우 콜드) | 마지막 공 다음은 0 이고 그 공의 득점은 넣습니다. 다만 **기대 득점 표를 만들 때는 각 경기의 마지막 반이닝을 뺍니다.** 3아웃 전에 끝날 수 있어 남은 득점이 덜 세어지기 때문입니다(2024: 반이닝 12,819개 중 721개). |
| 반이닝 구분 | (경기 ID, 이닝, 초/말) 로 묶습니다. 연장 이닝도 같습니다. |
| 볼 4 이상 | 데이터 오류입니다(2024 3건). 3으로 봅니다. |
| 구종이 빈 공 | 표 만들기에는 씁니다. 가치 표에는 넣지 않습니다(2024 464개). |
| 스위치 타자(양) | 투수 반대쪽 타석으로 셉니다. 우투수 상대면 L, 좌투수 상대면 R 입니다(usage 와 같은 규칙). |

2024 시험 결과(리그 전체, 투수 쪽 +): 슬라이더 +297점(100구당 +0.61), 직구 +120(+0.13), 체인지업
+22(+0.10), 포크 +18(+0.11), 커터 +25(+0.27), 커브 −62(−0.33), 투심 −50(−0.40).

## 4. 정할 것(evan)

| 번호 | 질문 | 권장 | 이유 |
|---|---|---|---|
| D1 | 폭투·포일·보크를 직전 공에 붙일까요? | 붙이지 않음 | 사건 행이 따로 있어 어느 공 몫인지 짐작해야 합니다. "공 자체의 결과"만 재는 편이 설명하기 쉽습니다. |
| D2 | 리그 합을 0으로 맞출까요(센터링)? | 맞추지 않음 | 사건 몫이 빠져서 2024 리그 합은 +333점(100구당 +0.14)입니다. 차이가 작고, 맞추면 "실제로 막은 점수"라는 뜻이 흐려집니다. |
| D3 | 기대 득점 표를 시즌별로 만들까요? | 시즌별 | 점수 환경이 해마다 다릅니다. 가장 드문 칸도 공이 몇 개는 있고, 드문 칸은 가치 합에 주는 영향도 작습니다. |
| D4 | 표를 어디에 둘까요? | MySQL 에만 | 사이트 API 는 MySQL 을 읽습니다. D1 은 5단계에서 정리할 예정이라 새 표를 만들지 않습니다. |
| D5 | 기대 득점 표도 저장할까요? | 저장 | 시즌당 288행으로 작습니다. 가치가 이상해 보일 때 확인할 수 있고, 데이터 탐색 페이지에서도 보입니다. |

## 5. 표

MySQL `bstats` 에 새로 만듭니다(evan 허락 뒤).

    pitch_run_value
      season      SMALLINT     시즌
      pitcher_ID  INT          투수 ID
      pitch_type  VARCHAR(20)  구종(arsenal·usage 와 같은 한글)
      stands      CHAR(1)      타자 손 L/R(스위치 타자는 위 규칙)
      n           INT          공 수
      rv          DOUBLE       가치 합(점, 투수 쪽 +)
      PRIMARY KEY (season, pitcher_ID, pitch_type, stands)

    run_expectancy
      season, bases TINYINT(0~7, 1루=1·2루=2·3루=4), outs, balls, strikes  → PRIMARY KEY
      re DOUBLE  기대 득점
      n  INT     그 상태의 공 수

- 쓰기는 수집 계정(bstats_loader), 읽기는 API 계정(bstats_api)입니다. 새 표에도 권한이 닿는지 만든 뒤 확인합니다.
- 시즌 단위로 바꿉니다. 한 트랜잭션에서 그 시즌 행을 지우고 새로 넣습니다.

## 6. 계산 작업

- 새 스크립트 `data_collection/pitch_run_value.py`
  - `--season YYYY`: 한 시즌을 다시 만듭니다.
  - `--current`: 올해만 다시 만듭니다(매일 단계).
  - `--from 2016 --to 2025`: 처음 한 번 채웁니다.
- 한 시즌을 MySQL 에서 읽어(약 23만 행) Python 에서 계산합니다. 2024 시험에서 읽기·계산 모두 수십 초
  안이었습니다. D1 은 읽지 않습니다.
- 계산 부분(반이닝 묶기, 기대 득점 표, 공 하나 가치, 묶어 더하기)은 DB 와 떨어진 순수 함수로 두고 시험합니다.
- 매일: `daily.yml` 의 PBP 적재·games 적재 뒤, 캐시 비우기 앞에 단계를 하나 넣습니다. 실행 기록(record_job_run)
  키를 남기고, 실패해도 다른 단계는 막지 않습니다(다른 파생 단계와 같게).
- 이 단계를 넣기 전에 DB 세션(dk-analytics-28)에 알리고 겹치는지 확인합니다.
- 계보: `database/lineage_writes.json` 에 스크립트(reads: play_by_play, writes: 두 표)를 적고
  `build_lineage` 와 pytest 를 다시 돌립니다. API 주소의 unused_routes 는 화면 쪽에서 정리합니다.

## 7. API

    GET /players/{id}/pitch_values?season=YYYY

    { "player_id": "65933", "season": 2026,
      "rows": [ { "pitch_type": "직구", "n_l": 512, "rv_l": 3.1, "n_r": 940, "rv_r": -1.2,
                  "n": 1452, "rv": 1.9 } ] }

- 표에서 읽기만 합니다. 한 투수 한 시즌이라 구종 수 × 2 행입니다.
- rv 는 소수 첫째 자리로 맞춥니다. n 이 많은 구종부터, 같으면 구종 이름 순입니다.
- season 형식 오류 400, 2016 전이나 수집 안 한 시즌 404, 선수 없음 404, 그 시즌 공이 없으면 `rows: []`.
- 캐시는 movement_avg 와 같습니다(지난 시즌 엣지 30일, 올해 하루).
- 시험: 응답 모양·정렬·반올림·L/R 합치기를 가짜 DB 로 시험합니다.

## 8. 하지 않는 것

- 100구당 가치 같은 비율 값은 API 에 넣지 않습니다. n 과 rv 가 있어 화면이 계산할 수 있습니다.
- 타자 쪽 가치, 구종별 리그 순위는 이번 범위가 아닙니다.
- 2016 전 시즌은 만들지 않습니다(요청 범위).
