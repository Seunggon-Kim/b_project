## 1. 배경

2026-07-14에 AWS 무료 플랜이 종료되면서 EC2 인스턴스가 정지했습니다. `https://bstats.duckdns.org/kbo/` 가 그날부터 접속되지 않습니다.

AWS 계정은 2026-10-12까지 유료 전환하지 않으면 삭제됩니다. Oracle Cloud Always Free 가입을 시도했으나 계정 생성 단계에서 두 번 실패했고 지원팀 문의 상태입니다. 한국 리전은 신규 무료 계정 목록에 없어 도쿄를 선택했으나 그것과 무관하게 막혔습니다.

**예산 0원이 절대 조건입니다.** VPS, 도메인 구입, 하드웨어 구입은 선택지에서 제외합니다.

2015~2024 와 2026 의 **원천** 데이터는 EC2 에만 있었고 지금은 접근할 수 없습니다. 로컬 어느 경로에도
사본이 없음을 확인했습니다(`Desktop`·`Downloads`·`Documents` 전체에서 5MB 이상 SQLite 파일 검색).

다만 API 가 서빙에 실제로 쓰는 파생 테이블 두 개는 위 표대로 덤프에 온전히 남아 있어 복원했습니다.
그래서 **wRC+ 비교 화면은 2015~2026 전 시즌이 살아 있고**, PBP·공식기록에 의존하는 화면만 2025 로 제한됩니다.

한 가지 부작용을 기록해 둡니다. `/wrc/seasons` 는 시즌 목록을 `play_by_play` 에서 뽑아 파생 테이블과
조인합니다(`api/main.py:834`). PBP 가 2025 뿐이라 화면의 시즌 셀렉터에는 2025 만 나옵니다. 데이터는
살아 있어 `?season=2019` 처럼 직접 지정하면 정상 응답합니다. 원천을 다시 수집하면 자동으로 풀리므로
**코드는 고치지 않습니다.** 지금 고치면 골든 비교의 정답지 기준이 흔들립니다.

## 2. 목표와 비목표

### 목표

- 현재 사이트의 **기능을 그대로** 되살립니다. 엔드포인트 29개, 페이지 7개 전부입니다.
- **운영 비용 0원**을 영구히 유지합니다.
- 서버 관리를 없앱니다. nginx, systemd, certbot, iptables, 배포 스크립트가 모두 불필요해집니다.

### 비목표

- 기능 추가나 화면 개편은 하지 않습니다. 이식에만 집중합니다.
- 성능 최적화는 무료 한도를 지키는 선에서만 합니다.
- `bstats.duckdns.org` 주소 유지는 포기합니다. DuckDNS가 CNAME을 지원하지 않아 Cloudflare Pages에 연결할 수 없습니다.

## 4. 아키텍처

```
[GitHub Actions]  Python 크롤러 9종 (Selenium 포함) 그대로 실행
       |
       |  wrangler d1 execute --remote
       v
[Cloudflare D1]   SQLite 호환 DB. 127MB, 237,873행
       ^
       |  조회
[Workers]         api/main.py 1,565줄을 JS로 이식. 엔드포인트 29개
       ^
       |
[Pages]           dashboard_js 정적 파일. API 주소만 교체
[R2]              선수 사진, 테이블 CSV 사전 생성본
```

주소는 `<프로젝트명>.pages.dev` 를 사용합니다. 무료이고 고정이며 HTTPS가 자동입니다.

### 재작성 범위

| 대상 | 처리 |
|---|---|
| `api/main.py` (1,565줄) | **JS로 이식.** 유일한 언어 재작성 대상 |
| 크롤러 9종 중 7종 (Python) | **변경 없음.** GitHub Actions에서 실행 |
| `selenium_batter_scraper.py`, `selenium_pitcher_scraper.py` | **Selenium 제거, HTTP 직접 호출로 전환** (5장) |
| `park_factors/` 파이프라인 | **변경 없음.** Actions에서 실행 |
| `dashboard_js/` 7개 페이지 | API 베이스 URL만 교체 |
| SQL 쿼리문 | **변경 없음.** D1이 SQLite 호환 |
| `deploy.sh`, `auto_deploy_poll.sh` | **삭제.** Pages가 push 감지해 자동 배포 |
| nginx, systemd, certbot, iptables | **삭제.** 불필요 |

### 왜 무거운 계산을 Worker에서 하지 않는가

Workers 무료 플랜은 호출당 CPU가 10ms입니다. 그러나 현재 구조가 이미 이 제약에 맞습니다. 파크팩터와 wRC+는 크론이 미리 계산해 `wrc_plus_comparison` 테이블에 적재하고, API는 그것을 읽기만 합니다. 무거운 계산은 Actions에 남기고 Worker는 조회와 직렬화만 담당합니다.

### API를 Pages Functions가 아닌 별도 Worker로 두는 이유

Pages의 정적 파일 서빙은 대역폭 제한이 없습니다. API를 Pages Functions로 만들면 정적 요청까지 Workers 일일 10만 요청 한도에 포함될 수 있습니다. API를 독립 Worker로 분리하면 정적 서빙이 한도를 소비하지 않습니다.

### 워크플로 구성

현재 크론 9개는 시각을 나눠 돌지만 실제로는 의존 체인입니다. pbp가 끝나야 games 보강이 되고, 그래야 park_factors가 정확합니다. 하나로 묶습니다.

```
daily.yml    매일 1회 순차 실행
             official_stats -> pbp -> games 보강 -> player_detector
             -> cleanup -> registry_sync -> park_factors
             -> D1 적재 -> R2 CSV 갱신 -> 실행 시각 기록

monthly.yml  매월 1일: player_info
```

각 단계는 독립적으로 실패할 수 있게 합니다. `official_stats` 가 실패해도 `pbp` 는 진행합니다.

### 공식 기록 수집을 Selenium에서 HTTP 직접 호출로 전환

현재 `official_stats` 만 Selenium을 씁니다. 대상은 두 페이지입니다.

```
Record/Player/HitterBasic/Basic1.aspx
Record/Player/PitcherBasic/Basic1.aspx
```

ASP.NET WebForms 페이지라 드롭다운과 페이지 넘김이 postback으로 동작해 브라우저가 필요했습니다. 이런 페이지는 대개 `__VIEWSTATE`, `__EVENTVALIDATION`, `__EVENTTARGET` 을 포함한 POST 요청으로 직접 호출할 수 있습니다.

이 프로젝트는 이미 같은 사이트를 브라우저 없이 호출하고 있습니다.

```
/ws/Main.asmx/GetKboGameList        (api/main.py)
/ws/Schedule.asmx/GetScheduleList   (data_collection/futures_schedule.py)
```

전환 시 효과입니다.

| 항목 | Selenium | HTTP 직접 호출 |
|---|---|---|
| Actions 분 | 월 약 450분 | **월 약 30분** |
| 1회 실행 시간 | 약 15분 | 1분 미만 |
| 필요 자원 | Chromium, chromedriver, 메모리 1GB | `requests` 만 |
| 안정성 | 브라우저 타이밍 이슈로 흔들림 | 안정적 |

부수 효과로 커밋 `d6f0232` 에서 추가한 `CHROMEDRIVER_PATH` 패치가 불필요해집니다. Oracle ARM 대응용이었는데 Selenium 자체가 사라지므로 의미가 없어집니다.

비용은 두 페이지의 postback 구조를 파악하는 작업입니다. KBO가 페이지 구조를 바꾸면 깨지지만, 그 점은 Selenium도 동일합니다.

**주의**: 이 전환은 브라우저 지문 기반 차단은 우회하지만 **IP 대역 차단은 우회하지 못합니다.** 위험 1의 완전한 해결책이 아닙니다.

### D1 적재 방식

Actions가 `wrangler d1 execute --remote` 로 SQL을 전송합니다. Cloudflare API 토큰은 GitHub Secrets에 둡니다.

일일 쓰기량 추정입니다.

```
PBP           경기 5개 x 약 300플레이 = 약 1,500행
공식 기록     타자 398 + 투수 281 upsert = 약 680행
파생 지표     수백 행
합계          약 3,000행   (한도 100,000행/일)
```

### 최초 적재는 10일에 나눕니다

> **[정정 2026-08-17] 당초 "3일" 로 적었으나 실측 결과 10일입니다.**

D1 무료 쓰기 한도가 하루 10만 행인데, 한 행을 넣을 때 계상되는 쓰기는 `1 + 그 테이블의
인덱스 수` 입니다. 문서에 "Indexes will add an additional written row" 로 명시돼 있고
실측으로도 확인했습니다. `play_by_play` 는 인덱스 3개라 행당 4 입니다.

| 항목 | 값 |
|---|---|
| 넣을 행 | 237,971 |
| 계상되는 쓰기 | **930,840** |
| 하루 예산 | 95,000 (한도 100,000 에서 여유 5,000) |
| 소요 | **10일** |

일회성 작업이고 비용은 0원입니다. 이 기간에는 사이트를 공개하지 않습니다.

적재 진행은 `migration/out/.progress` 에 파일 단위로 남아, 매일 같은 명령을 다시 실행하면
이어서 들어갑니다.

### 인덱스는 적재 전에 만듭니다

**적재를 마치고 인덱스를 만드는 순서는 쓸 수 없습니다.** 1,000행 테이블에 `CREATE INDEX`
하나를 실행하니 `rows_written` 이 1,001 이었습니다. 229,667행이면 단일 DDL 하나가 하루
한도를 그 자체로 넘는데, DDL 은 며칠에 나눠 실행할 수 없습니다. 인덱스를 먼저 만들어 두면
같은 비용이 행 단위로 쪼개져 여러 날에 나뉩니다.

인덱스는 로컬에 이미 있는 세 개만 옮깁니다.

```sql
CREATE INDEX idx_pbp_game    ON play_by_play(gameID);      -- games 조인, 시즌 커버 스캔
CREATE INDEX idx_pbp_batter  ON play_by_play(batter_ID);   -- 타자 조회
CREATE INDEX idx_pbp_pitcher ON play_by_play(pitcher_ID);  -- 투수 조회
```

당초 설계에 있던 `game_date` 기반 인덱스는 넣지 않습니다. `api/main.py` 의 play_by_play
쿼리는 시즌을 전부 `substr(gameID,1,4)` 로 거르고 `game_date` 로 거르는 쿼리가 하나도
없습니다. 한 번도 쓰이지 않을 인덱스에 적재 일수를 더 쓸 이유가 없습니다.

이식 과정에서 실제 쿼리 패턴을 보고 인덱스를 추가합니다.

### CSV 전체 내보내기

`/db/table/{table_name}/csv?limit=0` 은 테이블 전체를 반환합니다. `play_by_play` 요청 시 Worker의 CPU 10ms, 요청당 D1 쿼리 50개, 메모리 128MB를 모두 초과합니다.

Actions가 매일 테이블별 CSV를 생성해 gzip 압축 후 R2에 올려둡니다. Worker는 R2 링크로 리다이렉트합니다.

| 요청 | 처리 |
|---|---|
| `?limit=0` (전체) | R2 사전 생성 파일로 302 리다이렉트 |
| `?limit=N` (부분) | Worker가 즉석 생성 |
| 작은 테이블 (`players` 585행 등) | Worker가 즉석 생성 |

프론트엔드와 URL은 변경하지 않습니다. R2는 저장 10GB 무료이고 전송료가 없습니다. `play_by_play` CSV는 압축 시 10MB 안팎으로 예상합니다.

현재 EC2는 요청마다 22만 행을 즉석 생성합니다. nginx 타임아웃이 180초로 설정된 것이 그 부담을 보여줍니다. 사전 생성 방식이 더 빠릅니다.

**동작 차이 한 가지**: R2 파일은 마지막 일일 갱신 시점 기준입니다. 다만 이 데이터는 하루 한 번만 변경되므로 실질적 차이가 없습니다.

## 6. 무료 한도 대비 사용량

## 7. 위험과 대응

### 위험 1. KBO 사이트가 GitHub Actions를 차단할 수 있습니다

현재 Selenium 크롤러는 서울 EC2에서 실행됩니다. GitHub Actions 러너는 해외 데이터센터 IP입니다. 국내 사이트가 해외 데이터센터 트래픽을 차단하는 사례가 흔합니다.

발생 시 매일 02:00 공식 기록 수집이 실패해 타자·투수 성적이 갱신되지 않습니다.

**대응은 아래 순서로 시도합니다.**

| 순서 | 방법 | 뚫리는 경우 |
|---|---|---|
| 1 | **HTTP 직접 호출로 전환** (5장 참조) | 브라우저 지문·헤드리스 탐지가 원인일 때 |
| 2 | **Cloudflare Worker에서 호출** | IP 대역 차단이지만 Cloudflare 대역은 열려 있을 때. GitHub 러너는 Azure 대역이라 판정이 다를 수 있습니다. 단 CPU 10ms 안에 VIEWSTATE 파싱과 페이지 순회가 끝나야 합니다 |
| 3 | **집 PC 작업 스케줄러** | 위 둘이 모두 실패할 때. 한국 IP가 필요한 경우의 유일한 무료 수단입니다 |

3번을 쓰더라도 PC를 24시간 켜둘 필요는 없습니다. 하루 한 번 켜져 있을 때 실행되면 됩니다. 나머지 설계는 그대로 유지됩니다.

**검토했으나 채택하지 않은 방법**

- **네이버 API로 대체**: 타자 42개, 투수 57개 컬럼을 채워야 하는데 `blown_save`, `wins_game_relieved`, `balk`, `go_ao` 같은 세부 항목을 네이버가 제공하지 않습니다. 기능 동일 목표와 충돌합니다.
- **무료 프록시**: 신뢰성과 보안 문제가 있어 제외합니다.

**확인 시점**: M1에서 DB 재구축을 Actions로 실행하며 판명됩니다.

#### 판정 (2026-08-17) — 차단되지 않았습니다

`.github/workflows/daily.yml` 을 GitHub Actions 에서 실행해 확인했습니다
(run 31986867040, `ubuntu-latest`).

|---|---|---|

러너에서 실제로 받아 냈다는 뜻이므로, 계획 D 의 재크롤링이 실현 가능하다는 근거가 됩니다.

두 가지를 뒤에서 확인해야 합니다.

- **컬럼 수**: CSV 는 37컬럼인데 `kbo_official_batter_stats` 는 42컬럼입니다
  (`created_at`·`updated_at` 을 빼면 40). 차이 3개가 적재 단계에서 계산되는

- **Actions 분**: 타자 수집 한 번에 약 7분입니다. 매일 돌리면 월 210분으로

**따라서 대응 사다리를 쓰지 않습니다.** 크롤러 9종을 설계대로 Actions 에서 돌립니다.
2번(Cloudflare Worker 경유)도, 3번(집 PC 작업 스케줄러)도 필요 없습니다. 예산 0원

HTTP 직접 호출로의 전환(5장)은 급한 과제가 아니게 되었습니다. Selenium 이 러너에서
그대로 동작하므로 M6 의 최적화 항목으로 남깁니다. 다만 Actions 분을 아끼는 효과가

**이 판정은 오늘 시점의 것입니다.** KBO 가 나중에 정책을 바꾸면 daily 워크플로가
실패로 드러납니다. 그때 위 사다리를 순서대로 시도하면 됩니다. 판정 스크립트를

## 10. 테스트 전략: 골든 응답 비교

이식 작업의 성공 기준은 **같은 요청에 같은 응답**입니다. 화면을 눈으로 확인하는 대신 기계적으로 검증합니다.

```
1. 로컬에서 현재 FastAPI를 실행합니다 (로컬 SQLite 사용)
2. 29개 엔드포인트를 아래 파라미터 규칙으로 호출해 응답 JSON을 저장합니다  <- 정답지
3. 이식한 Worker에 동일한 요청을 보냅니다
4. 응답을 정답지와 비교합니다
```

전제 조건은 로컬 DB와 D1의 데이터가 동일해야 한다는 것입니다. M2의 최초 적재 직후에 정답지를 생성합니다.

### 파라미터 조합 규칙

엔드포인트마다 아래 경우를 모두 생성합니다.

- **파라미터 없음**: 기본값 동작 확인
- **경로 파라미터**: 실제 존재하는 값 3개(국내 타자, 국내 투수, 외국인 선수 각 1명)와 존재하지 않는 값 1개
- **시즌 파라미터**: 데이터가 있는 시즌 2개와 데이터가 없는 시즌 1개
- **경계값**: `limit=1`, `min_pa=0`, `min_pa=999`(결과 0건), 날짜 범위의 첫날과 마지막날
- **정렬·방향 파라미터**: 지원하는 값 전부

결과 0건과 존재하지 않는 ID는 반드시 포함합니다. 이식 과정에서 NULL과 빈 배열 처리가 어긋나는 일이 가장 흔합니다.

### 비교 규칙

- **부동소수점**: 상대 오차 `1e-9` 이내면 같다고 봅니다. 화면에 표시되는 지표는 소수점 3자리까지가 대부분이라 이 기준이면 충분합니다
- **정수·문자열**: 완전 일치를 요구합니다. 특히 `player_id` 는 문자열과 정수 혼용 이력이 있어 타입까지 비교합니다
- **배열 순서**: `ORDER BY` 가 명시된 쿼리는 순서까지 비교합니다. 명시되지 않은 쿼리는 정렬 후 비교합니다
- **NULL**: `null`, 빈 문자열, `0` 을 구분해 비교합니다

### HTTP 전환은 M6 로 갑니다

| M1 결과 | 실행 시점 | 성격 |
|---|---|---|
| Actions에서 KBO 접속 성공 | **M6** | 최적화. Actions 분을 15배 아끼고 안정성을 올립니다 |
| Actions에서 KBO 차단 | M1 직후 즉시 | 위험 1의 1차 대응 |

**M1 판정 결과 접속에 성공했으므로 위 표의 첫 줄이 적용됩니다.** HTTP 전환은 급한
과제가 아니라 M6 의 최적화 항목입니다.

M1에서 DB 재구축을 Actions로 실행하는 이유는, 어차피 필요한 작업이므로 이를 통해 위험 1이 첫 단계에서 드러나기 때문입니다.

### M2 가 3일에서 10일로 늘었습니다

인덱스가 쓰기 행을 배로 늘려 전체 계상 쓰기가 930,840행입니다. 6장의 적재 항목을
보십시오. 비용은 0원 그대로이고 걸리는 시간만 늘어납니다. **M2 는 M3·M4 와 병행할 수
있습니다.** API 이식은 로컬 SQLite 로도 개발할 수 있고, 골든 정답지는 이미 떠 두었기
때문입니다. 적재 완료를 기다리며 놀 필요가 없습니다.

M4가 가장 깁니다. wRC+ 계열 8개와 DB 탐색 3개가 무거운 편입니다.
