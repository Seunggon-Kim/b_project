## 목표

수집 작업(daily·roster·monthly·weekly)이 D1 과 Cloud SQL MySQL 에 같이 씁니다.
사이트는 3단계까지 D1 을 계속 읽습니다. MySQL 은 그동안 D1 과 같은 상태를
유지하고, 매일 대조해 같다는 것을 확인합니다. 7일 연속 대조가 깨끗하면
3단계(API 를 MySQL 로)로 넘어갑니다.

## 로드맵과 달라진 점(2026-10-02 조사 결과)

| 로드맵 항목 | 바뀐 판단 | 이유 |
|---|---|---|
| `shard_backfill` 의 meta 미갱신 수정 | 하지 않음. 대신 백필 단계를 daily 에서 뺌(2A) | 2008~2014 백필은 2026-08-29 에 끝났습니다(커서 20111031·20141111, 남은 경기 0). 더 쓰지 않으므로 meta 가 다시 낡지 않습니다. 매일 남은 경기 수를 세는 D1 읽기만 남아 있습니다 |
| 포스트시즌 날짜 버그 "2026 포스트시즌 전에" | 급하지 않음. 그래도 2A 첫 일로 고침 | 버그는 13자 gameID(2015년까지)에서만 납니다. 2026 포스트시즌은 17자라 날짜가 맞게 나옵니다. 깨진 행은 끝난 백필이 넣은 2008~2015 포스트시즌뿐입니다 |
| D1 의 깨진 포스트시즌 26,450행 복구 | 하지 않음 | 복구하면 그 행이 D1 의 시즌 날짜 범위로 들어와 지금 사이트 숫자가 바뀔 수 있습니다. MySQL 쪽은 1단계에서 이미 고쳤습니다. 시즌 집계에 넣을지는 3단계 확인 목록에 있습니다 |
| GitHub Actions 접속: 서비스 계정 키(시크릿) | 키 없는 연동(Workload Identity Federation) 권장 | 오래 사는 키를 공개 저장소의 시크릿에 두지 않습니다. 실무 표준이기도 합니다. 막히면 키 방식으로 돌아갑니다(2B Task 1) |
| 1단계 보강 4건 | 2건(인덱스 이월, 적재기 정리)만 2C 에서 함. 2건(`--append` 보호, 스냅샷 지문)은 보류 | 따라잡기를 전체 재이전이 아니라 "공용 표 다시 넣기 + 빠진 날 PBP 다시 수집"으로 합니다. 보류한 두 건은 샤드를 이어 받거나 `--resume` 할 때만 쓰입니다. 전체 재이전이 필요해지면 그때 합니다 |
| (새로 발견) 공용 D1 인덱스 13개가 MySQL 에 없음 | 2C 에서 옮김 | 1단계 내려받기가 인덱스를 안 가져왔습니다. 3단계 API 속도에 필요합니다 |
| (새로 필요) `play_by_play.game_date` 인덱스 | 2C 에서 만듦 | MySQL 은 400만 행이 한 표라 `DELETE … WHERE game_date = ?` 가 인덱스 없이는 표 전체를 훑습니다 |
| 주 1회 파크팩터 작업 | MySQL 에서 내려받게 바꾸고 다시 켬(2B) | D1 에서 내려받으면 400만 행 읽기라 무료 한도를 거의 다 씁니다. MySQL 은 읽기 한도가 없습니다 |
| `d1_load.py` 와 같은 이름의 `db_load.py` 를 만들고 import 한 줄만 바꿈 | D1 코드는 그대로 두고 `mysql_sink.py` 의 `mirror()` 를 더함 | 이중 적재 동안은 두 곳에 다 써야 해서 import 를 바꿔 끼울 수 없습니다. D1 코드를 안 건드리므로 사이트 쪽 위험이 없습니다. 전환(5단계) 때 D1 줄을 지우면 MySQL 만 남습니다 |

## 2단계에서 하지 않는 것

- 수집기의 **D1 읽기**(`teams`·`kbo_roster`·`players`·`games` 조회, `d1_columns` 등 약 10곳)를 MySQL 로 바꾸는 일. 이중 적재 동안은 D1 이 정본이라 D1 에서 읽습니다. 전환(5단계) 계획서에서 `Sink.query` 로 바꿉니다. 그때 `heal_player_photos.py` 의 별칭 없는 파생 표 2곳도 고칩니다.
- `team_ranks.py`(MySQL 예약어 `rank` 열). 어느 워크플로도 부르지 않습니다.
- 2015~2023 PBP 샤드 다시 받기. 1단계 스냅샷의 8/29 사본을 그대로 씁니다. 그 뒤 그 시즌에 쓰는 작업이 없고, 세 샤드의 D1 행 수 기록(2026-08-18)도 그대로입니다. 매일 대조의 전체 행 수가 계속 확인합니다.

## 순서와 관문

```
2A  수집기 버그·안정화 ──────────────┐   (D1 쪽만 바뀜. 바로 시작 가능)
2C  1단계 도구 보강 ─────────────────┤
2B  Task 1 GCP·MySQL 준비 ───────────┤   (evan 승인·GitHub 시크릿 등록 필요)
2B  Task 2~8 코드 ───────────────────┤   (MYSQL_MIRROR 가 꺼진 채로 main 에 들어가도 D1 동작은 그대로)
                                     ▼
2B  Task 9 켜기 + 따라잡기 + 7일 대조 ──▶ 3단계
```

- 2A·2C·2B 코드는 서로 독립이라 어느 것부터 해도 됩니다. 다만 2B 의
  `sync_players` 이중 적재(Task 5)는 2A Task 4(0-3)가 먼저 들어가야
  D1 과 MySQL 이 같은 규칙으로 움직입니다.
- 2B Task 9(켜기)는 2A·2C 와 2B Task 1~8 이 모두 main 에 들어간 뒤에 합니다.
- 각 계획서는 자기 브랜치·worktree 에서 실행합니다. 다른 세션(페이지 수정)과
  작업 폴더를 같이 쓰지 않습니다.
- push·병합은 계획서 하나가 끝날 때마다 evan 에게 묻습니다.

## 켜고 끄는 스위치

이중 적재는 저장소 변수 하나로 켜고 끕니다.

| 이름 | 종류 | 값 | 뜻 |
|---|---|---|---|
| `MYSQL_MIRROR` | Actions 변수(vars) | `on` | 워크플로가 MySQL 에 접속하고 이중 적재합니다 |
| (없음 또는 다른 값) | | | MySQL 에 손대지 않습니다. 코드가 main 에 있어도 D1 동작은 지금과 같습니다 |

문제가 생기면 이 변수를 지우는 것으로 즉시 되돌립니다. D1 쪽은 어느 경우에도
그대로 돕니다(MySQL 실패가 D1 적재를 막지 않습니다). 다만 실패는 워크플로
마지막 판정에서 빨간색으로 드러납니다.

## 비용

- Cloud SQL 은 이미 과금 중입니다(월 1.5만~2만 원). 이중 적재로 늘지 않습니다.
- 주 1회 내려받기로 Cloud SQL → 인터넷 전송이 주 1GB 안팎 생깁니다(주 100~200원 수준).
- GitHub Actions 는 공개 저장소라 무료입니다.
- D1 읽기는 대조 때문에 하루 약 7만 행 늘고, 백필 단계·주간 내려받기가 빠져
  주 400만 행 이상 줄어듭니다.

## 끝났다고 보는 기준

- 수집 4개 워크플로가 MySQL 에도 쓰고, 실패하면 빨간색으로 보입니다.
- 매일 대조(`migration/mysql/reconcile.py`)가 7일 연속 차이 0 입니다.

- MySQL 에 공용 인덱스 13개와 `idx_pbp_game_date` 가 있습니다.
